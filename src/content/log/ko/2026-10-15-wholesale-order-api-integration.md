## 무엇을 했나

쇼핑몰에 주문이 들어오면 도매처에서 물건을 떼야 한다. 지금까지는 이 일을 모두 손으로 했다. 주문 알림을 보고, 도매 사이트에서 상품과 옵션을 고르고, 받는 사람 주소를 넣고 결제한다. 한 건에 5분쯤 걸렸고, 밤에 들어온 주문은 아침까지 멈춰 있었다.

도매처(도매꾹 Open API)가 Private API로 주문서를 만드는 기능을 제공해서 그것을 붙였다. 10월 11일 4시간 동안 문서를 찾아 읽고, 스펙을 역추적하고, 모듈을 만들고 회귀 테스트까지 했다. 만든 것은 다음과 같다.

- 도매처 API 모듈: 로그인(세션 캐시), 잔액 조회, 구매 내역, 송장 조회, 발주
- 쇼핑몰 주문에서 상품·옵션·수량·수령인을 뽑아 발주 지시서로 바꾸는 변환기
- 회귀 테스트 33건(구분자 조립, 필수값 검증, 전화번호 형식)

안전장치는 세 겹으로 뒀다. 발주 함수는 기본값이 "실행 안 함"이고, 잔액이 모자라면 호출하기 전에 멈추며, 쇼핑몰 주문번호를 키로 기록해 같은 주문을 두 번 떼지 않는다. 그런데 세 번째 장치는 동작하지 않고 있었다. DB 연결 함수는 컨텍스트 매니저(`with` 문과 함께 써야 하는 함수)인데, 코드가 반환값을 그대로 쓰고 있었다. 실제 호출 전에 이 문제를 찾았다.

## 결과

10월 12일 세 번째 주문을 처음으로 API로 뗐다. 도매처 호출은 한 번에 성공했다(성공 1, 실패 0).

| 구간 | 시각 | 걸린 시간 |
|---|---|---|
| 결제 → 주문 알림 | 07:39 → 08:29 | 50분 |
| 알림 → 발주 | 08:29 → 10:54 | 2시간 25분 |
| 발주 → 쇼핑몰 발주확인 | 10:54:35 → 10:55:15 | 40초 |

주문 확인은 매시 29분에 하는데, 이 주문은 07:29 직후에 들어와 알림까지 50분이 걸렸다. 줄어든 것은 물건을 '떼는' 시간이고, 줄지 않은 것은 '떼도 되나'를 사람이 확인하는 시간이다. 첫 실제 호출이라 일부러 단계마다 멈췄다. 먼저 실행 안 함 모드로 돌려 금액과 남을 잔액을 봤다. 수령인 정보는 값을 화면에 찍지 않고 형식만 검사했다. 실행 직전에는 결제 상태, 취소 요청, 같은 주문서가 이미 있는지, 가격이 그사이 바뀌었는지를 다시 봤다. 실행한 뒤에는 도매처 주문서, 예치금 잔액, 원장 세 곳이 서로 맞는지 다시 읽었다.

도매 결제는 13,760원(도매가 10,760원 + 배송비 3,000원)이었고, 예치금은 30,000원에서 16,240원이 됐다. 정산예정 금액이 15,665원이라 이 주문의 마진은 15,665 − 13,760 = 1,905원이다(광고비 제외).

첫 실행은 도매처까지 가지도 못했다. 이 작업을 같이 하는 Claude Code의 자동 실행 모드가 이 명령을 실제 거래로 분류해 막았다. 대화에서 사람이 승인했어도 막혔고, 사람이 직접 설정에 허용 규칙을 넣어야 풀렸다. 규칙은 주문번호를 지정한 실행만 허용하도록 좁게 넣었다. 내 코드의 안전장치 세 겹 바깥에 도구 쪽 장치가 하나 더 있었던 셈이다.

작업하면서 알게 된 것은 이렇다.

- 기능을 찾으려고 mode 이름 288개 조합을 모두 호출했다. 권한이 있는 기능만 "파라미터 오류"를 돌려줘서 6개를 찾았다. 하지만 잔액 조회는 내 단어 목록에 이름이 없어서 찾지 못했다. 나중에 보니 문서에 한 줄로 적혀 있었다. 이 과정에서 호출 한도에 걸려 한동안 재고 동기화도 막혔다.
- 주문 문자열은 샘플만 보고 수직바 1개로 끊는다고 읽었고, `P`를 상품유형으로 하드코딩했다. 가이드 문서를 보니 `||`로 끊은 5개 항목이었고, `P`는 배송비 부담주체였다. 지금까지 주문이 모두 선결제라 결과가 우연히 맞았을 뿐이고, 무료배송 상품을 떼면 틀렸을 것이다.
- 기능마다 메서드와 버전이 달랐다(구매 내역은 GET 4.0, 잔액 조회는 POST 1.0). 구매 내역을 POST로 보내면 "파라미터가 없거나 잘못되었습니다"라는 응답이 온다.
- API에는 장바구니가 없다. 주문서 생성 호출 한 번이 곧 결제다. 결제는 선충전 예치금으로만 되고 충전 API는 없다. 그래서 자동 발주가 쓸 수 있는 돈의 상한은 사람이 충전해 둔 금액이다.

발송도 이어서 처리했다. 세 번째 주문은 결제(07:39)부터 쇼핑몰 발송처리(17:34)까지 약 10시간이 걸렸다. 송장은 택배사 배송조회에 집화 기록이 뜬 뒤에만 넣기로 정했다. 도매 사이트에 송장번호가 떴다는 것은 공급사가 송장을 뽑았다는 뜻이지, 택배사가 물건을 받았다는 뜻은 아니기 때문이다. 쇼핑몰은 내가 보낸 발송일 대신 송장을 처음 등록한 시각을 발송일로 기록했다.

## 다음 행동

택배사 배송조회 화면을 브라우저로 따로 열어 집화를 확인하고 있다. 집화 확인, 발송처리, 되읽기를 스크립트 하나로 묶고, 그 뒤 주문 한 건이 결제부터 발송처리까지 걸리는 시간을 구간별로 기록한다.

## 정리

**측정한 것**
- 비용: 연동 작업에 든 현금 지출 0원(도매 결제 13,760원은 판매 원가라 제외)
- 시간: 4시간(10월 11일 문서 탐색부터 회귀 테스트까지. 10월 12일 첫 실제 호출은 제외)
- 결과: 첫 API 발주는 성공 1, 실패 0이었다. 발주부터 발주확인까지 40초였고, 알림부터 발주까지는 2시간 25분이었다.

**확실한 것**
- 이 API에는 장바구니가 없어서 주문서 생성 한 번이 곧 결제다.
- 결제는 예치금으로만 되고 충전 API가 없어, 쓸 수 있는 돈의 상한은 충전 금액이다.
- 샘플 코드만 보고 읽은 구분자와 항목 의미가 가이드 문서와 달랐다.
- 중복 발주 방지 장치가 동작하지 않던 것을 실제 호출 전에 찾았다.

**아직 모르는 것**
- 한 상자로 합포장된 두 주문에서 운송장 품목 칸에 첫 주문 상품만 찍히는지는 아직 모른다. 구매자가 받아 봐야 확정된다.
- 쇼핑몰 응답의 `isReceiverAddressChanged`가 주문 뒤 배송지 변경을 알려 주는 값인지는 추측이다. 다음 주문에서 확인한다.
- 사람이 확인하는 2시간 25분을 얼마나 줄일 수 있는지는 아직 재지 않았다.
