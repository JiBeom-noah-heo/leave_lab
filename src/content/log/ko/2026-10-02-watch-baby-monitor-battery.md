## 무엇을 했나

목표는 워치를 아이 옆에 소음 감지기로 1시간 켜 둘 때 배터리를 15% 이하로 쓰는 것이었다.

첫 측정은 디버그 빌드로 했고, 1시간에 18%를 써서 목표를 넘겼다. 무선 디버깅을 끄고 다시 재 봐도 16%였다. 화면은 3분밖에 켜지지 않았다. 그런데 앱 CPU 사용이 71분 중 48분이었고, 그중 24분이 화면(UI) 스레드였다. 이 숫자를 보고 "잠깐" 했다.

원인은 소리 레벨 처리 방식이었다. 100ms마다 바뀌는 소리 레벨을 앱 상태 전체에 넣어 두었다. 그래서 화면이 꺼져 있어도 상태를 받는 곳이 초당 10번 깨어났다. 레벨을 따로 떼어 냈고, 화면은 보일 때만 250ms 간격으로 갱신하게 바꿨다.

앱이 잡는 WakeLock도 살펴봤다. 녹음하는 동안에는 오디오 시스템 WakeLock과 겹쳐서, 빼도 줄어드는 양이 거의 없었다. 그래서 유지했다.

## 결과

| 측정 | 빌드 | 1시간 소모 |
|---|---|---|
| 1차 | 디버그, 무선 디버깅 켬 | 18% |
| 2차 | 디버그, 무선 디버깅 끔 | 16% |
| 3차 | 릴리스 + 수정 후 | **10%** (73→63%) |

3차 측정 조건은 다음과 같다.

| 항목 | 값 |
|---|---|
| 측정 시간 | 1시간 0분 |
| 화면 켜짐 | 2분 46초 |
| 방전량 | 28.7mAh (용량 295mAh) |
| 소음 알림 | 8회 |

화면이 꺼진 동안의 CPU 사용은 코어 하나 기준 약 68%에서 6.9%로 줄었다. 릴리스 빌드에 미리 컴파일까지 한 상태에서 잰 값이다. 디버그 빌드는 대부분 인터프리터로 돈다. 그래서 배터리는 릴리스 빌드로 재야 실제 사용과 비슷하다.

같은 날 밤에는 baseline profile을 붙였다. 측정 때 쓴 미리 컴파일은 adb 명령으로 강제로 한 것이다. 실제 설치에서는 기기가 쉴 때까지 이 컴파일이 적용되지 않는다. 그래서 앱에 자주 쓰는 코드 목록(baseline profile)을 넣었다.

이 비교는 폰 감지기로 했다. 화면을 끈 상태에서 60초 동안 코어 1개 기준 CPU를 쟀다.

| 조건 | 화면 꺼짐 CPU |
|---|---|
| 목록 없음 | 2.6% |
| 목록 적용 | 1.9~2.0% |

약 25% 줄었다.

여기서 헛걸음을 두 번 했다. 첫째, 규칙을 넣었더니 프로필 파일이 오히려 작아졌다. 직접 풀어서 세 봤더니 압축 차이였다. 둘째, 다시 컴파일해도 실행 중인 앱은 옛 코드로 돌았다. 그래서 첫 비교는 무효였다.

## 다음 행동

실제 설치에서도 미리 컴파일되도록 baseline profile을 검토하고, 밤새(8~12시간) 켜 두는 시험을 한다.
